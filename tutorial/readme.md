## 第 1 节：项目介绍与背景

### 主题

**browser-use 是什么？为什么浏览器 Agent 很重要？**

### 本节目标

让观众理解：

- **真实任务发生在网页里**：搜索资料、填写表单、查询价格、操作后台、提交申请等任务都依赖浏览器。
- **普通 Chatbot 只能回答问题**：它不能直接点击网页、输入内容、读取页面状态。
- **只会调用 API 的 Agent 还不够**：很多业务系统没有 API，或者 API 不开放。
- **浏览器是 Agent 走向真实任务的重要入口**：浏览器让 Agent 可以进入真实网页环境。
- **browser-use 和 Selenium、Playwright 的区别**：传统自动化依赖固定脚本，browser-use 让 LLM 根据页面状态动态决策。

### 讲解切入点

可以从这个问题开始：

> 大模型会聊天、会总结、会写代码，但很多真实任务发生在网页里。那大模型怎么才能像人一样操作网页？

然后引出 browser-use 的核心价值：

> 它把浏览器变成了 Agent 的执行环境，让 Agent 可以观察网页、理解页面、选择动作、点击输入，并循环完成任务。

### 推荐环境安装

项目开发建议使用 `uv`：

```bash
uv venv --python 3.11
source .venv/bin/activate
uv sync
```

安装浏览器运行依赖：

```bash
uvx browser-use install
```

配置环境变量：

```bash
BROWSER_USE_API_KEY=
```

推荐默认使用 `ChatBrowserUse`，它是为浏览器自动化任务优化的模型接口。

### 最小 Demo

推荐演示任务：

```python
from browser_use import Agent, Browser, ChatBrowserUse
import asyncio


async def main():
    browser = Browser()
    agent = Agent(
        task="Find the number of stars of the browser-use repo",
        llm=ChatBrowserUse(),
        browser=browser,
    )
    await agent.run()


if __name__ == "__main__":
    asyncio.run(main())
```

### 讲解重点

- **`Browser()`**：负责启动和管理浏览器。
- **`ChatBrowserUse()`**：负责提供浏览器自动化任务需要的模型能力。
- **`Agent(...)`**：把任务、模型和浏览器组合起来。
- **`agent.run()`**：启动多步执行循环。

## 第 3 节：browser-use 的整体工作流

### 主题

**Agent 是如何一步步操作浏览器的？**

### 本节目标

讲清楚 browser-use 的核心执行闭环：

```text
用户输入任务
    ↓
Agent 接收 task
    ↓
Browser 启动浏览器
    ↓
读取当前页面状态
    ↓
提取可点击元素、文本、输入框等信息
    ↓
把页面状态交给 LLM
    ↓
LLM 决定下一步动作
    ↓
Controller / Browser 执行动作
    ↓
页面发生变化
    ↓
继续观察、决策、执行
    ↓
直到任务完成
```

### 核心概念

browser-use 的本质不是一次性问答，而是一个循环：

```text
Observe → Think → Act → Observe
```

也可以理解为：

```text
观察页面 → 模型决策 → 执行动作 → 页面更新 → 再观察
```

它和 ReAct Agent 很像，只不过普通 ReAct 调用的是搜索、计算器、数据库等工具，而 browser-use 调用的是浏览器动作。

### 讲解重点

- **页面状态如何进入模型**：DOM、文本、交互元素、截图等信息会被整理为模型可理解的上下文。
- **模型如何输出动作**：LLM 不只是回答问题，而是要选择下一步可执行动作。
- **浏览器如何执行动作**：动作会被映射成点击、输入、滚动、等待、提取等浏览器操作。
- **为什么需要多轮循环**：网页任务通常不是一步完成，而是需要不断观察新页面并调整策略。

7. 浏览器如何执行动作

## 第 5 节：源码结构总览

### 主题

**从目录结构理解 browser-use 的架构**

### 本节目标

让观众先建立源码地图，而不是一上来陷入细节。

### 推荐讲解结构

```text
browser_use/
├── agent/          # Agent 主循环、消息管理、提示词、任务判断
├── browser/        # 浏览器启动、会话管理、页面控制
├── dom/            # 页面状态解析、DOM 快照、元素提取
├── controller/     # 把模型动作转成具体浏览器操作
├── llm/            # 不同大模型供应商适配
├── tools/          # 自定义工具和扩展能力
├── mcp/            # MCP 集成
├── filesystem/     # 文件系统相关能力
├── sandbox/        # 沙盒执行相关能力
└── telemetry/      # 运行日志和追踪
```

### 模块职责

- **`agent`**：大脑，负责规划、消息管理和执行循环。
- **`browser`**：身体，负责启动浏览器、管理页面和会话。
- **`dom`**：眼睛，负责看懂网页、抽取页面状态和交互元素。
- **`controller`**：手，负责把模型动作转成点击、输入、滚动等实际操作。
- **`llm`**：模型接口，负责适配不同大模型供应商。
- **`tools`**：外部能力扩展，支持业务工具、自定义动作和结构化输出。
- **`mcp`**：连接 MCP 生态，扩展外部工具能力。
- **`filesystem`**：处理文件读写、下载、上传等文件相关能力。
- **`sandbox`**：面向云端或隔离环境的运行能力。
- **`telemetry`**：运行日志、指标和追踪。

### 一次任务如何穿过这些模块

```text
Agent 接收任务
    ↓
Browser 打开页面
    ↓
DOM 提取页面状态
    ↓
Agent 构造消息并调用 LLM
    ↓
LLM 返回动作
    ↓
Controller 执行动作
    ↓
Browser 页面变化
    ↓
DOM 再次提取状态
    ↓
Agent 判断是否继续
```

## 第 6 节：核心模块拆解：Agent、Browser、DOM、Controller

### 主题

**browser-use 的核心四件套**

### 本节目标

深入理解四个核心模块的职责与协作关系：

```text
Agent      ：负责想
Browser    ：负责打开网页
DOM        ：负责看网页
Controller ：负责动手
```

### 1. Agent 模块

重点讲：

- **接收任务**
- **维护历史消息**
- **构造 prompt**
- **调用 LLM**
- **解析模型输出**
- **判断任务是否完成**
- **控制循环次数**
- **处理失败重试**

可以把 Agent 理解为整个系统的调度中心。

### 2. Browser 模块

重点讲：

- **启动浏览器**
- **管理页面**
- **复用 session**
- **处理 profile、cookie、认证**
- **截图和录制**
- **等待页面加载**
- **和底层浏览器自动化能力交互**

Browser 模块更接近底层执行环境。

### 3. DOM 模块

重点讲：

- **把网页变成结构化状态**
- **提取可点击元素**
- **识别输入框、按钮、链接等交互元素**
- **给元素编号**
- **压缩页面内容，让它适合 LLM 阅读**
- **减少无关 DOM 对模型上下文的干扰**

DOM 模块决定了 Agent “看到什么”。

### 4. Controller 模块

重点讲：

- **接收模型输出的动作**
- **校验动作格式**
- **找到对应页面元素**
- **调用浏览器执行点击、输入、滚动等操作**
- **返回执行结果**
- **把失败原因反馈给 Agent**

Controller 模块决定了 Agent “怎么动手”。

### 一次点击动作链路

```text
LLM 输出 click 动作
    ↓
Controller 校验动作参数
    ↓
根据元素编号找到 DOM 元素
    ↓
Browser 执行点击
    ↓
页面跳转或局部更新
    ↓
DOM 重新提取页面状态
    ↓
Agent 进入下一轮决策
```

### 一次输入动作链路

```text
LLM 输出 input/type 动作
    ↓
Controller 校验输入内容和目标元素
    ↓
Browser 聚焦输入框
    ↓
写入文本
    ↓
页面状态变化
    ↓
Agent 继续观察
```

## 第 7 节：模型适配、自定义工具与二次开发

### 方向 1：换模型

可讲的模型方向：

- **Browser Use 模型**

- **Claude**
- **Gemini**
- **Qwen**
- **DeepSeek**
- **Ollama 本地模型**
- **OpenRouter / LiteLLM 等聚合接口**

讲解重点：

> 浏览器 Agent 对模型的结构化输出能力要求很高。模型不只是要会回答，还要稳定地产生可执行动作。

推荐默认展示 `ChatBrowserUse`，因为它更适合浏览器自动化任务。

### 方向 2：加自定义工具

可以扩展的工具：

- **保存结果到 Markdown**
- **写入 JSON**
- **调用数据库**
- **调用飞书 / Notion**
- **调用邮件系统**
- **把网页内容整理成教程大纲**
- **把搜索结果保存为结构化报告**

示例方向：

```python
from browser_use import Agent, ChatBrowserUse, Tools

tools = Tools()


@tools.action("Save important findings to a markdown file")
def save_to_markdown(content: str) -> str:
    with open("result.md", "w", encoding="utf-8") as f:
        f.write(content)
    return "Saved to result.md"
```

然后传给 Agent：

```python
agent = Agent(
    task="Search browser-use project information and save a summary",
    llm=ChatBrowserUse(),
    tools=tools,
)
```

## 第 8 节：项目边界、生产化问题与总结

### 主题

**browser-use 能做什么，不能做什么？**

### 本节目标

帮助观众建立工程判断力，理解 Demo 和真实生产环境之间的差距。

### browser-use 适合的场景

- **网页资料收集**
- **后台系统辅助操作**
- **重复性网页任务**
- **表单填写**
- **网页内容提取**
- **轻量级浏览器自动化**
- **需要 LLM 动态决策的网页流程**

### browser-use 不适合直接裸跑的场景

- **强验证码场景**
- **强风控网站**
- **高并发浏览器任务**
- **对稳定性要求极高的核心链路**
- **必须严格确定性执行的流程**
- **涉及敏感数据但缺少安全控制的场景**

### 常见失败原因

1. **登录态处理复杂**
2. **验证码阻断任务**
3. **动态网页导致元素定位失败**
4. **页面结构变化影响稳定性**
5. **多任务并发消耗大量浏览器资源**
6. **模型输出动作格式不稳定**
7. **页面加载慢或异步渲染导致状态不一致**
8. **任务描述不清晰导致 Agent 走偏**

### 从 Demo 到生产还缺什么

真实生产环境通常还需要：

- **浏览器池**
- **代理和网络策略**
- **任务队列**
- **失败重试**
- **日志与监控**
- **权限与安全控制**
- **成本控制**
- **模型输出校验**
- **人工接管机制**
- **任务结果审计**
